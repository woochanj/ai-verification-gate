# 검증 기준 → 테스트

기준 파일이 정본이다. 테스트는 기준을 옮긴 것이고, 기준보다 많지도 적지도 않다.

## 순서
1. `criteria/*.yaml`에서 해당 id의 `pass`·`fail`을 그대로 읽는다. 요약하거나 짐작하지 않는다.
2. 대상 화면을 Playwright MCP로 실제로 열어 요소(`data-test`)와 흐름을 눈으로 확인한다. 다른 화면 코드를 보고 추측해서 쓰지 않는다.
3. API가 걸린 기준이면 실제 요청을 보내 응답 모양을 확인한다.
4. 테스트 제목은 `[기준 id] 기준 title`로 쓴다. 리포터가 이 id로 판정을 묶는다.
5. 판정에 쓴 값을 `evidence()`로 남긴다. 사람이 근거만 보고 판정을 다시 내릴 수 있어야 한다.
6. 실행해서 통과·실패를 확인하고, 실패면 원인이 테스트인지 제품인지 나눠 적는다.

## 규칙
- **빠뜨리지 않는다:** `pass`에 적힌 조건은 전부 assertion으로 만든다.
- **더하지 않는다:** `pass`에 없는 것은 검증하지 않는다. "보는 김에"는 사유가 아니다. 기준과 무관한 이유로 빨간불이 나면 게이트를 믿을 수 없게 된다.
- **실패를 숨기지 않는다:** 막히면 데이터를 바꿔 풀고, 그래도 안 되면 실패로 남긴다. assertion을 주석 처리하거나 재시도로 통과시키지 않는다.
- **데이터를 박지 않는다:** 상품 id·가격을 테스트에 쓰지 않는다. API에서 조건으로 고른다(예: `in_stock`이 false인 첫 상품).
- **판정할 대상이 없으면 skip하고 이유를 적는다.** 게이트는 blocker의 skip을 미판정으로 보고 막는다.
